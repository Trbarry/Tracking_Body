PRIM-ID: PRIM-0503 — "Trojan" super-root game: an INVALID game that embeds the CORRECT per-chain output root accepts unmodified honest proofs
Source contracts: OptimismPortal2 v6.1.0; SuperFaultDisputeGame v0.8.0 (type 9 impl 0x19AF533Cc2A2A55786DCB8672aA5717e64213208, respected on OP Mainnet / Ink / Unichain since before U21, unchanged by U21); DisputeGameFactory v1.6.1; reference client `op-node/withdrawals/utils.go`
Exact functions: `OptimismPortal2.proveWithdrawalTransaction` (:441-450: for super games only `rootClaimByChainId(systemConfig.l2ChainId())` is compared with the supplied output-root proof); `SuperFaultDisputeGame.initialize` (:251-341: only checks `keccak(extraData) == rootClaim`, version byte, length % 64, seq > anchor) and `rootClaimByChainId` (:809-819, first match wins, no sortedness/uniqueness/chain-set check); `Encoding.decodeSuperRootProof` (Encoding.sol:308-345); `DisputeGameFactory.create`; then `deleteProvenWithdrawal`
Trigger: permissionless `DGF.create{value: 0.08 ether}(9, keccak(extra), extra)` with `extra = 0x01 ‖ T ‖ (10, R_real(T)) ‖ (999, junk)` (or a duplicated chain-10 entry) — a non-canonical super root for timestamp T whose chain-10 component is the true output root
Attacker-controlled inputs: the whole super-root preimage (chain list, order, duplicates, timestamp)
Required state: respected game type is a permissionless super type (OP Mainnet, Ink, Unichain: type 9; Soneium type 5 is proposer-gated → not exposed); T > anchor sequence number
State mutation: new respected, proper game `G_t` with `wasRespectedGameTypeWhenCreated = true`. Any prover (the withdrawal owner, a relayer, a bot) whose client selects `G_t` gets `provenWithdrawals[h][prover] = (G_t, now)` with a fully honest proof. When the honest challenger counters the root and the game resolves CHALLENGER_WINS (≥ 3.5 d later), that proof is permanently dead and deletable by anyone (PRIM-0501); the prover must prove again and wait a fresh 7 d.
External calls: none beyond the normal prove path
Cross-contract dependency: game validity is a property of the WHOLE super root (decided off-chain by the fault-proof program / challenger comparing hashes), while the portal consumes ONE component. Under the legacy single-output-root types (0, 8) the two coincided: a game whose root equals the true output root at its claimed block is valid, so an honest proof could not be accepted by an invalid game.
Broken or weakened assumption: "if the portal accepts a proof built from true L2 state, the game it was proven against is true". Also: the monorepo's reference selector `ProveWithdrawalParametersFaultProofs` → `findLatestWithdrawalGameCandidate` (op-node/withdrawals/utils.go:114-246) walks back from the newest game of the respected type, takes the first whose sequence ≥ the withdrawal's and that contains the chain, and only checks `provenOutputRoot == candidate.OutputRoot` (:169) — it would pick the trojan. It backs the official CLI `op-chain-ops/cmd/withdrawal/prove.go` and `op-devstack/dsl/bridge.go`.
Candidate compositions: (1) sustained withdrawal-delay griefing of every client that proves against "the latest covering game": attacker posts one trojan after each honest proposal (~hourly on OP Mainnet); (2) with a third-party forwarder/relayer contract whose prove entry point is permissionless: overwrite the contract's good proof slot with a trojan proof; (3) for the dispute-game lane: non-canonical roots (extra chain, duplicate chain id, far-future timestamp) are creatable at will — real third-party invalid type-9 games already exist on OP Mainnet (idx 21288 claims timestamp 2000000000; idx 20184 claims 1822124842; weekly 0xdeadbeef… test games by 0xaa08d4…; 80 CHALLENGER_WINS games among the 11,561 non-retired ones) — all safety rests on the challenger.
Evidence: `TrojanGameTest.test_trojan_game_accepts_honest_proof_then_dies` (test/poc/lane05/Trojan.t.sol) on the `l1` fork: real calldata of mainnet prove tx 0x1214545b79a6e2decfca0ec8bd9668038d8603f71acb5e093c8b153eff8b5c0a (119.59 ETH messenger withdrawal, submitter 0xb9b397fb…), only `_disputeGameIndex` changed to the attacker's game → accepted; both the extra-chain and the duplicate-chain variants are created successfully; after CHALLENGER_WINS `checkWithdrawal` reverts `InvalidRootClaim` and a random address deletes the proof. Trace: evidence/lane05-trojan-trace.txt. Bond accounting in the same test: the first uncountered counter-claimant is credited the creator's 0.08 ETH plus its own 0.0876 ETH.
Confidence: high for the on-chain behaviour; medium for exploit economics (bond recovery needs the attacker's own counter-claim to be the honest one and to stay uncountered — not simulated); unverified which production front-ends/SDKs auto-select the newest game.
Reason it may be benign: no funds move and nothing is frozen permanently; the victim (or his client) chooses the game index and can choose an older resolved or honest-proposer game; it is the same class as "a multi-chain super root is invalid because of another chain", which is inherent to super roots. Honest score as a candidate: +2 permissionless, +2 real-impl fork repro, +2 cross-contract invariant, +1 deterministic, +1 multi-chain, −3 no eligible impact (delay/griefing = suppressed "temporary inconvenience"), −2 needs victim-side game selection ⇒ ≈ 3. Not filed as a candidate.
