PRIM-ID: PRIM-0403 - `OptimismPortal_L1CDMCallFailed` is keyed on the SENDER only; exact trigger table

Source contracts: OptimismPortal2 v6.1.0; L1CrossDomainMessenger v2.13.0; L2CrossDomainMessenger v2.2.1 (live L2)
Exact functions: OptimismPortal2.sol:651-653 `if (!success && _tx.sender == Predeploys.L2_CROSS_DOMAIN_MESSENGER) revert`
Trigger table (all reproduced on the l1 fork, fabricated proofs unless stated):
  | sender        | target        | inner call        | portal result                                   |
  | L2CDM         | L1CDM         | relay returns     | finalized (message successful OR failed-recorded)|
  | L2CDM         | L1CDM         | relay reverts     | revert L1CDMCallFailed, stays proven             |
  | L2CDM         | anything else | fails             | revert L1CDMCallFailed (target irrelevant)       |
  | not L2CDM     | L1CDM         | relay reverts     | finalized, success=false, value re-locked        |
  | not L2CDM     | L1CDM, value 0, data = relayMessage(of a FAILED msg) | finalized; the message is replayed |
  Order matters: the ESTIMATION_ADDRESS revert (:635) precedes it; both precede the event and the re-lock.
Complete list of `relayMessage` reverts reachable from the portal path (CrossDomainMessenger.sol): paused (:222,
  same source as the portal pause: SystemConfig.paused -> portal.ethLockbox().paused()); version >= 2 (:225);
  legacy v0 already relayed (:231); `assert(msg.value == _value)` (:242); `assert(!failedMessages[h])` (:243);
  unsafe target = L1CDM or portal (:250); already successful (:254); out of gas anywhere; ESTIMATION origin.
  Every non-reverting exit writes `successfulMessages` (:292) or `failedMessages` (:269, :295).
Attacker-controlled inputs: none that reach a persistent revert for someone else's message (see REJ-0403).
Required state: -
State mutation: none on revert.
Broken or weakened assumption: before v9 a messenger withdrawal whose relay reverted was consumed; now it is
  "proven, never finalizable" if the revert is deterministic (message to L1CDM/portal, relayed legacy message).
  Its ETH stays in the lockbox instead of being re-locked - same place, documented in the code comment.
Candidate compositions: a future L1CDM change that adds a new deterministic revert (e.g. a target block-list)
  would now freeze instead of consume; any chain whose L2CDM `otherMessenger` is not its live L1CDM.
Evidence: `Fab.t.sol::test_cond_*`, `::test_messenger_failed_then_replay_and_no_double`;
  L2 side: `L2Side.t.sol` (deployed L2CDM v2.2.1 refuses to relay to the message passer or to itself, and
  `sendMessage` always targets `0x25ace71c…`), so "sender == L2CDM, target != L1CDM" is unreachable on OP Mainnet.
Confidence: high.
Reason it may be benign: intended behaviour; the sender check is sufficient on the deployed L2 code.
