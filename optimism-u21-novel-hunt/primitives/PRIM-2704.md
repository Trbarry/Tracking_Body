# PRIM-2704

PRIM-ID: PRIM-2704 — anchors are shared across types and ASR registration does not re-check the game's embedded ASR

Source contracts: `AnchorStateRegistry` and all dispute games exposing `gameData`/`anchorStateRegistry`.

Exact functions: `anchors`, `getAnchorRoot`, `isGameRegistered`, `isGameClaimValid`, `setAnchorState`.

Trigger: Anyone calls `setAnchorState(game)` with a newer, claim-valid factory game.

Attacker-controlled inputs: Choice of an already claim-valid game; game creation inputs where the type is permissionless.

Required state: The game must match the ASR's current factory UUID mapping, be non-retired/unblacklisted, have snapshotted respect, be finalized, and be `DEFENDER_WINS`.

State mutation: The single `anchorGame` pointer changes for every game type.

External calls: ASR reads game data/status/root/sequence and queries its configured factory.

Cross-contract dependency: Factory game arguments embed an ASR, but `isGameRegistered` only reconstructs the factory lookup. The former explicit `game.anchorStateRegistry() == address(this)` check was removed.

Broken or weakened assumption: Factory-domain membership, rather than an explicit registry-address equality check, is the security-domain boundary.

Candidate compositions: A future migration/upgrade that reuses one DGF across ASRs or changes game args non-atomically could admit a game from the wrong registry into the shared anchor.

Evidence: `packages/contracts-bedrock/src/dispute/AnchorStateRegistry.sol:188-237,328-372`; on chain, the current OP factory type-9 args embed `0x23B2...D113`; the planned v9 migration instead deploys a fresh DGF/ASR pair (`OPContractsManagerMigrator.sol:191-263`).

Confidence: High for the primitive; low for any present exploit.

Reason it may be benign: Today's factory args point to the same ASR, and the planned migration uses a fresh factory atomically, so no cross-domain registered game was found.
