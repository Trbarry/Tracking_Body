PRIM-ID: PRIM-0502 — `proofSubmitters[h]` is an append-only, unauthenticated, never-pruned array
Source contracts: OptimismPortal2 v6.1.0
Exact functions: `proveWithdrawalTransaction` (push at :487), `numProofSubmitters` (:800), public getter `proofSubmitters(bytes32,uint256)`, `deleteProvenWithdrawal` (:725, no array write)
Trigger: any successful prove by anyone for any withdrawal hash
Attacker-controlled inputs: the pushed address is `msg.sender`; the withdrawal hash is arbitrary (attacker can prove a victim's real withdrawal against any proper+respected+non-CW game, including his own 0.08 ETH invalid game whose fabricated output root contains the hash — `_createGameFor` in Lifecycle.t.sol builds such a root with a single-leaf trie)
Required state: not paused
State mutation: `proofSubmitters[h].push(msg.sender)` every time — same submitter re-proving pushes a duplicate; deletion leaves the entry (stale pointer to an empty `provenWithdrawals` slot); 43 entries measured, no upper bound
External calls: none
Cross-contract dependency: none on-chain. No contract under `src/` reads the array (grep: only the push and the length getter). Off-chain only: clients that resolve "the" proof of a withdrawal via `numProofSubmitters`/`proofSubmitters(h, n-1)`.
Broken or weakened assumption: "`proofSubmitters[h]` enumerates the live proofs of h" is false: entries may be duplicates, deleted, or third-party proofs against doomed games; `numProofSubmitters` over-counts.
Candidate compositions: UI/SDK-level status confusion (attacker keeps his address last; after his game loses and the proof is deleted the last entry resolves to `(0x0, 0)`); none found on-chain.
Evidence: `CrossVersionTest.test_shadow_proof_does_not_affect_victim` (victim slot byte-identical before/after, array = [victim, attacker], attacker entry stale after delete, victim finalizes), `test_reprove_overwrites_and_duplicates` (index 0 == index 1; 43 entries; finalize gas 205,097 independent of length; re-prove gas ~263k)
Confidence: high
Reason it may be benign: every on-chain read is keyed by `(hash, submitter)`; finalization names the submitter explicitly; no loop over the array exists, so growth cannot make any call unaffordable. Off-chain tooling impact is "temporary inconvenience" (suppressed class) and predates U21 (array exists since Portal2 3.x); U21 only adds the stale-after-delete case.
