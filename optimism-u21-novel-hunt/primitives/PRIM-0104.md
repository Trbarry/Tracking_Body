PRIM-ID: PRIM-0104
Title: SUPER_PERMISSIONED games are authorised by `tx.origin`, cost no bond and are DEFENDER_WINS at creation; U21 rotated the OP Mainnet proposer to an EOA that also runs the permissionless proposer

Source contracts: `src/dispute/SuperPermissionedDisputeGame.sol` (v1.1.0, impl `0x5C3eb47cB0174aea522a2a9Ae79487139A53D691`, same before and after U21), `src/dispute/DisputeGameFactory.sol`.

Exact functions: `SuperPermissionedDisputeGame.initialize` (line 60 `if (tx.origin != proposer()) revert BadAuth();`, lines 66-70 `resolvedAt = createdAt; status = DEFENDER_WINS`), `DisputeGameFactory.create` (callable by anyone, `msg.value == initBonds[5] == 0`).

Trigger: any contract executing inside a transaction signed by the proposer key calls `DisputeGameFactory.create(5, rootClaim, extraData)`.

Attacker-controlled inputs: `rootClaim` and the super-root proof in `extraData` (only constrained by `hash(extraData) == rootClaim` and `l2SequenceNumber > anchor`).

Required state: code controlled by the attacker runs in a proposer-originated transaction. Proposers per `gameArgs(5)`: OP `0xc27ba3E0Fc01567a5E57Ae0c391AA98cECBA5bE0` (new in U21, was `0x473300df...`), Ink `0x3832bfbE...`, Soneium `0x400c164C...`, Unichain `0x86B392ca...`.

State mutation: a registered type-5 game with an arbitrary super root that is already resolved for the defender. It is respected only where `respectedGameType == 5` (Soneium today; OP/Ink/Unichain only if the guardian falls back to type 5).

External calls: ASR `getAnchorRoot`, `respectedGameType`.

Cross-contract dependency: only the guardian blacklist/retirement inside the 302400 s finality airgap (plus the 7-day proof maturity) stands between such a game and withdrawals.

Broken or weakened assumption: "only the proposer can propose" is really "only code running under the proposer's `tx.origin` can propose".

Candidate compositions: a call path in the proposer's routine transactions that yields control to third-party code. None found: the Soneium proposer's nonce equals the factory `gameCount` (8533 at N-1, 8537 at 26433900), i.e. it only ever calls `create`, and `create` / `initialize` make no call to untrusted code. Would need a different transaction type from that key.

Evidence: source lines above; `gameArgs(5)` at N-1 and N (`U21_INITIALIZER_CALLS.md` section 5); nonces via `cast nonce`.

Confidence: high (behaviour), very low (reachability).

Reason it may be benign: same `tx.origin` rule exists in `PermissionedDisputeGame` in v8 and earlier; permissioned games are trusted-proposer by design; reaching it needs the privileged key to run foreign code, which is outside the permissionless attacker model.
