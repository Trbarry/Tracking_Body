# PRIM-2402 — Messenger/Portal two-layer replay state and v9 atomic rollback

## Mechanism

The Portal owns a withdrawal-global finalized bit; the L1 messenger separately owns `failedMessages` and `successfulMessages` (`CrossDomainMessenger.sol:119-142`). Messenger target failure or its early gas/reentrancy branch records `failedMessages=true` and returns normally (`:256-306`). The Portal therefore sees a successful call to the messenger and may finalize the outer withdrawal. Anyone can later replay the message because `failedMessages=true`; successful replay sets `successfulMessages=true`, which then blocks every further relay even though the failed bit remains true (`:239-254,288-296`).

If the messenger reverts before either mapping is written, v9 Portal observes a false call and rolls back the entire finalization when `_tx.sender` is the L2 messenger (`OptimismPortal2.sol:639-653`). The proof and outer replay path survive.

## Local-fork evidence

- Failed application target: outer Portal finalized, messenger failed bit set, replay succeeded once, second messenger replay and second Portal finalization both reverted (`WithdrawalFinalization24.t.sol:359-399`).
- Messenger pre-record revert: Portal reverted with `OptimismPortal_L1CDMCallFailed`, and all three bits remained false (`:401-428`).
- Source tests independently encode the intended rollback (`test/L1/OptimismPortal2.t.sol:1824-1897`).

## Invariant result

No path was found where the Portal regards the messenger call as successful while the application is neither delivered nor represented by a messenger replay bit. No path was found to execute the same message twice: the messenger success bit and Portal global finalized bit are independent backstops.
