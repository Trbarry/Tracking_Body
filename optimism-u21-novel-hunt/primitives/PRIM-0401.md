PRIM-ID: PRIM-0401 - third party converts any mature messenger withdrawal into "failed in messenger" without delivery

Source contracts: OptimismPortal2 v6.1.0 (`0xb20b23af…`), L1CrossDomainMessenger v2.13.0 (proxy `0x25ace71c…`)
Exact functions: `OptimismPortal2.finalizeWithdrawalTransactionExternalProof` (src/L1/OptimismPortal2.sol:577),
  `CrossDomainMessenger.relayMessage` re-entrancy branch (src/universal/CrossDomainMessenger.sol:265-282)
Trigger: the attacker replays one of his own failed messages directly on the L1CDM (`xDomainMsgSender` is then
  non-default); the replay target (attacker contract) calls the portal's ExternalProof finalize for the victim's
  withdrawal. The portal is not inside a finalization (`l2Sender == DEFAULT`), so the guard at :594 passes; the
  nested `relayMessage` is "from the other messenger", hits `xDomainMsgSender != DEFAULT_L2_SENDER`, sets
  `failedMessages[hash] = true` and RETURNS, so the portal sees success and finalizes.
Attacker-controlled inputs: the moment; the victim withdrawal (any mature, valid proof of any submitter).
Required state: attacker owns one failed message whose target he controls (permissionless: send an L2->L1
  message to a contract that reverts once; 7-day wait). Victim withdrawal mature and game valid.
State mutation: `finalizedWithdrawals[wd] = true`; lockbox -value; L1CDM +value; `failedMessages[msg] = true`;
  `successfulMessages[msg]` stays false. Nothing is delivered.
External calls: portal -> lockbox.unlockETH -> portal.donateETH; portal -> L1CDM.relayMessage (returns early).
Cross-contract dependency: portal's guard is `l2Sender`, messenger's guard is `xDomainMsgSender`; they are
  independent, so "messenger busy, portal idle" is reachable.
Broken or weakened assumption: "a messenger withdrawal is executed when it is finalized". It is only *recorded*;
  custody of the ETH moves from the lockbox (pause/unlock-gated, authorised-portal-gated) to the L1CDM balance.
Candidate compositions: (a) any target that behaves differently on replay than on first delivery (e.g. reads
  `portal.l2Sender()`, which is the L2CDM on first delivery and 0xdEaD on replay); (b) anything that later treats
  L1CDM-held ETH differently from lockbox ETH (interop liquidity migration only moves the lockbox);
  (c) off-chain bridge UIs / monitors that assume `WithdrawalFinalized(success=true)` == delivered.
Evidence: `test/poc/lane04/Fab2.t.sol::test_forced_fail_via_nested_finalize_in_replay` - victim is the REAL
  2000 ETH withdrawal 0x8df3d52a…f241 (real proof by real submitter); attacker's own message uses a fabricated
  proof. Post-state: lockbox -2000 ETH, L1CDM +2000 ETH, failed=true, successful=false; then a permissionless
  replay delivers exactly once. `test_nested_finalize_inside_portal_relay_blocked` shows the same nesting from
  inside a portal-driven relay is blocked (OptimismPortal_NoReentrancy).
Confidence: high (reproduced on fork against deployed implementations).
Reason it may be benign: the message stays replayable by anyone, value is conserved, and the branch exists since
  Bedrock ("marks the message as failed to allow it to be replayed"). Griefing / UX only. Not a v9 regression.
