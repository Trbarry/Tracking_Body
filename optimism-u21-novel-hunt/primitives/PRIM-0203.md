PRIM-ID: PRIM-0203
Title: `deleteProvenWithdrawal` (new in v9) clears `provenWithdrawals[h][s]` but leaves `s` in `proofSubmitters[h]`

Source contracts: OptimismPortal2 v6.1.0 (`0xb20b23af..`), AnchorStateRegistry v4.0.0

Exact functions: `OptimismPortal2.deleteProvenWithdrawal(bytes32,address)` (src/L1/OptimismPortal2.sol:711-728);
`proveWithdrawalTransaction` push (:487); `numProofSubmitters` (:800-802); `checkWithdrawal` (:671-705).

Trigger: permissionless call, no pause check, once the stored game is `CHALLENGER_WINS` or blacklisted in the portal's
*current* ASR.

Attacker-controlled inputs: `_withdrawalHash`, `_proofSubmitter` (must name an existing entry).

Required state: `provenWithdrawals[h][s].timestamp != 0` and (`game.status() == CHALLENGER_WINS` ||
`anchorStateRegistry.isGameBlacklisted(game)`).

State mutation: `delete provenWithdrawals[h][s]` only. `proofSubmitters[h]` keeps the address forever (array is
append-only; re-proving appends a duplicate). After deletion `numProofSubmitters(h) >= 1` while
`provenWithdrawals(h, proofSubmitters(h, i))` is `(0, 0)`.

External calls: `game.status()` on the stored game (always a factory clone), `asr.isGameBlacklisted`.

Cross-contract dependency: "permanent" is relative to the portal's current ASR; after `migrateToSharedDisputeGame` the new
ASR has an empty blacklist, so proofs against games blacklisted in the old ASR stop being deletable (they are dead anyway:
`isGameRegistered` fails in the new factory).

Broken or weakened assumption: off-chain tooling that treats `numProofSubmitters(h) > 0` / the last `proofSubmitters`
element as "a live proof exists" (withdrawal status helpers, finalizer bots).

Candidate compositions: griefing of off-chain status only. On chain it cannot hurt a live proof: deletion is impossible
unless the game can never validate the withdrawal, and a re-proof overwrites the entry with a new game.

Evidence: `test_deleteProvenWithdrawalLeavesSubmitterResidue` (test/poc/lane02/U21WithdrawalBoundary.t.sol) on the block-N
fork with the real OP Mainnet entry h=`0xcb4d1cae..651d`, s=`0x47728c87..`, game `0x86512332..`: reverts
`OptimismPortal_DisputeGameNotInvalidated` while the game is neither lost nor blacklisted; after the Guardian's documented
`blacklistDisputeGame` (setup state production can be in) any address deletes it; `numProofSubmitters` stays 1,
`proofSubmitters(h,0)` still returns `s`, second delete reverts `OptimismPortal_Unproven`.

Confidence: high (behaviour); impact: none on funds.

Reason it may be benign: documented cleanup; proof is already unusable; no storage that `checkWithdrawal` reads is left
inconsistent.
