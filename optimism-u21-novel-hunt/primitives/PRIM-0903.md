Source contracts: src/dispute/SuperFaultDisputeGame.sol, src/libraries/Encoding.sol, src/dispute/AnchorStateRegistry.sol,
  src/L1/OptimismPortal2.sol, src/L1/opcm/OPContractsManagerUtils.sol

  uniqueness / ordering check), initialize (L278-279: only `hashSuperRootProof(extraData) == rootClaim`),
  Encoding.decodeSuperRootProof (L308-345: no ordering/duplicate validation), AnchorStateRegistry.isGameRegistered
  (L227-238: the `game.anchorStateRegistry() == address(this)` check was REMOVED, see comment L217-224),
  OptimismPortal2.proveWithdrawalTransaction (L441-445: `rootClaimByChainId(systemConfig.l2ChainId())`),
  OPContractsManagerUtils.makeGameArgs (super games get `l2ChainId = 0` in gameArgs).
Trigger: permissionless `DisputeGameFactory.create(9, rootClaim, extraData)` with a hand-built super-root preimage.
Attacker-controlled inputs: the full (chainId, outputRoot)[] list and timestamp of the proposed super root.
Required state: type 9 (SUPER_CANNON_KONA) respected — TRUE TODAY on OP Mainnet, Unichain and Ink.
State mutation: none by itself (a game is created).
External calls: n/a.
Cross-contract dependency (on-chain evidence, fork `l1` @26433900): `gameArgs(9)` of the OP Mainnet, Unichain and Ink DGFs are
  byte-identical except for ASR and DelayedWETH: same impl 0x19AF533C…, same absolutePrestate
  0x03e5a54835d39c1d83b198314473e1f111c3539c04f65c3e8a9b8ccebe3737c9, same VM 0xacc005dc…, trailing l2ChainId word = 0.
  So nothing in the game instance says which chain it is for; the only on-chain bindings are (i) which DGF created it,
  (ii) that DGF's ASR anchor lineage, (iii) the portal's `l2ChainId` lookup into the proposer-supplied list.
Broken or weakened assumption: "a game accepted by portal X commits to exactly one output root for chain X".
  On-chain, a super root with duplicate chain ids, extra chains, or a foreign chain set is well-formed; rejecting it is
  left entirely to the fault-proof program + an honest challenger (i.e. the fault path).
Candidate compositions (for the dispute / proof-program lanes, NOT verified here):
  - duplicate-chainId super root `[(10, fake), (10, real)]`: does kona-interop treat it as invalid? first-match wins on L1.
  - after migration both portals read the same shared game: a root list that is canonical for the program but
    ordered/duplicated differently from what `rootClaimByChainId` assumes.
  - any future deployment where two ASRs share one DGF (isGameRegistered no longer binds game to ASR; only
    `retirementTimestamp` separates them) — not the case on mainnet or in migrate() (new DGF + new ASR are both net-new).
Evidence: cast reads of `gameArgs(uint32)` / `gameImpls(uint32)` on DGFs 0xe5965Ab5…, 0x2F12d621…, 0x10d7B350…; file:line above.
Confidence: high for the facts; exploitability unknown (depends on off-chain program semantics).
Reason it may be benign: an invalid super root is challengeable; type-5 games are permissioned.
