PRIM-2308: CGT and zero-value branches sever ETH liability creation without rejecting surplus

Source contracts: OptimismPortal2, SystemConfig, OPContractsManagerMigrator

Exact functions: `depositTransaction`, `proveWithdrawalTransaction`, `finalizeWithdrawalTransactionExternalProof`, `migrateLiquidity`, `_migratePortal`

Trigger: CUSTOM_GAS_TOKEN enabled or transaction value zero.

Attacker-controlled inputs: Zero-value deposit/withdrawal data; donation amount.

Required state: CGT feature for guarded branches.

State mutation: CGT blocks positive `msg.value` deposit and positive-value proof/finalization, and blocks portal migration; zero-value messages remain possible. Donation/forced ETH can still create surplus.

External calls: None for donation; zero-value target call still executes during finalization.

Cross-contract dependency: Migrator refuses to put a CGT chain into the shared ETH pool.

Broken or weakened assumption: CGT mode does not mean the portal can never contain ETH; it means no ETH-backed protocol liability path is permitted.

Candidate compositions: Privileged post-deployment CGT enablement with historical ETH; surplus recovery; zero-value reentrancy.

Evidence: v9 `src/L1/OptimismPortal2.sol:406-409,500-512,583-589,741-759`; `src/L1/opcm/OPContractsManagerMigrator.sol:483-486`; fork `test_cgtModeRejectsETHLiabilityPathsButDonationStillAccepts`; live CGT=false.

Confidence: High for branches, low relevance to deployed OP configuration.

Reason it may be benign: Every positive-value liability path is rejected and the remaining ETH can only be unbacked surplus; changing CGT is privileged and discouraged post-deployment.
