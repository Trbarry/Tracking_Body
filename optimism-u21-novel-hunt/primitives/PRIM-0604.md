PRIM-ID: PRIM-0604 — SuperchainConfig accepts any identifier; non-lockbox identifiers are inert after v9 and the deputy module's post-check still passes
Source contracts: SuperchainConfig v2.5.0, DeputyPauseModule v2.1.0, SystemConfig v4.3.0
Exact functions: SuperchainConfig.pause(address) (no validation of the identifier); DeputyPauseModule.pause post-condition `SUPERCHAIN_CONFIG.paused(_identifier)` (src/safe/DeputyPauseModule.sol:180-183); SystemConfig.paused() (src/L1/SystemConfig.sol:574-576) no longer consults the portal identifier.
Trigger: Guardian/deputy pauses with identifier = OptimismPortal or SystemConfig address (the pre-v9 identifier for chains that had ETH_LOCKBOX off).
Attacker-controlled inputs: none
Required state: -
State mutation: pauseTimestamps[portal] set; no contract reads it
External calls: -
Cross-contract dependency: deputy pause messages are EIP-712 signed per identifier (`PauseMessage(bytes32 nonce,address identifier)`); a message pre-signed for a portal address executes "successfully" and pauses nothing.
Broken or weakened assumption: "PauseTriggered emitted => chain paused".
Candidate compositions: only as an incident-response delay on top of an independent bug.
Evidence: PauseMatrix.t.sol::test_identifier_consistency — `SC.pause(portal)` and `SC.pause(systemConfig)` leave all 7 getters false on all four chains. For the four U21 chains the identifier did NOT change: ETH_LOCKBOX was already true and portal.ethLockbox() already the same address at block 26430858 (evidence/lane06/state-pre-26430858.txt).
Confidence: high
Reason it may be benign: operator tooling issue, explicitly called out in the U21 notice (upgrade-21.mdx:86-87, 226); not applicable to the four upgraded chains.
