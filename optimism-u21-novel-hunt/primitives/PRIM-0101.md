PRIM-ID: PRIM-0101
Title: Output-root games created since 2025-07-24 are still claim-valid next to super-root games; U21 re-initialised the ASR without retiring them

Source contracts: `src/dispute/AnchorStateRegistry.sol` (v4.0.0, proxy `0x23B2C62946350F4246f9f9D027e071f0264FD113` on OP Mainnet; same shape on Ink/Soneium/Unichain), `src/L1/OptimismPortal2.sol` (v6.1.0), `src/L1/opcm/OPContractsManagerV2.sol`.

Exact functions: `AnchorStateRegistry.initialize` (retirement only when `retirementTimestamp == 0`, lines 124-132), `isGameRetired`, `isGameProper`, `isGameRespected`, `isGameClaimValid`, `setAnchorState`; `OptimismPortal2.proveWithdrawalTransaction` (branch `GameTypes.isSuperGame(...) ? rootClaimByChainId(l2ChainId) : rootClaim()`), `finalizeWithdrawalTransactionExternalProof`.

Trigger: anyone calls `proveWithdrawalTransaction(_tx, _disputeGameIndex, ...)` with the index of an old type-0 (CANNON) or type-8 (CANNON_KONA) game.

Attacker-controlled inputs: `_disputeGameIndex` (any of the ~21k registered games), the output-root proof and withdrawal proof.

Required state: game registered in the chain's DisputeGameFactory, created after `retirementTimestamp` (OP/Ink 1753379243, Soneium 1753380095, Unichain 1753380731), `wasRespectedGameTypeWhenCreated == true`, not blacklisted, status DEFENDER_WINS. All of this already holds on mainnet.

State mutation: `provenWithdrawals[hash][msg.sender]` written against a legacy game; later `finalizedWithdrawals[hash]`.

External calls: game `gameData()`, `status()`, `rootClaim()`, `createdAt()`; factory `games(...)`.

Cross-contract dependency: the ASR does not key validity on the current respected game type or on the game's proof system; the DisputeGameFactory keeps every historical game; the OPCM re-initialises the ASR on every upgrade but never moves `retirementTimestamp`.

Broken or weakened assumption: "after the switch to super-root games only super-root games matter". Two root formats with different `l2SequenceNumber` units (L2 block number for types 0/8, unix timestamp for types 5/9) coexist as valid in one registry.

Candidate compositions:
- any legacy game that resolved DEFENDER_WINS on a wrong root and was never blacklisted is still usable today (needs a scan of all type-0/8 games per chain; not done here);
- `setAnchorState` compares sequence numbers of mixed units; today block numbers (~1.6e8) are far below timestamps (~1.79e9), so a legacy game can never displace a super anchor - check any chain where that ordering could differ;
- after the planned `migrate`, the per-chain ASR is abandoned by the portal, which removes this surface for migrated chains.

Evidence:
- `cast call 0x23B2...D113 "isGameClaimValid(address)(bool)" 0x42002e33e38c8cfdEbC8A3CeC6aE304E024caf4f` -> `true` (DGF index 16000, type 0, created 1775585747); same for `0x2d060507c776259CCd0e2d589bE80Eb8024420f9` (index 19000, type 8, created 1786373507, `l2SequenceNumber` 155386797) on `l1` @ 26433900.
- `retirementTimestamp` unchanged N-1 -> N (`U21_INITIALIZER_CALLS.md` section 4, ASR slot 6).
- `OptimismPortal2.sol` prove path, non-super branch uses `disputeGameProxy.rootClaim()`.

Confidence: high that the state exists; low that it is exploitable.

Reason it may be benign: those games carry genuine, finalized output roots of the same chain; replay is blocked by `finalizedWithdrawals`; the behaviour predates U21 (the retirement rule is unchanged from v8) and is the documented reason retirement is decoupled from the respected type.
