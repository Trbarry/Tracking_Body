PRIM-2102: Atomic two-pass StorageSetter reinitialization

Source contracts: OPContractsManagerUtils, StorageSetter, ProxyAdmin, all 41 upgraded proxies.

Exact functions: `OPContractsManagerUtils.upgrade` (`OPContractsManagerUtils.sol:312-387`), `StorageSetter.setBytes32/getBytes32` (`StorageSetter.sol:25-42`).

Trigger: A ProxyAdmin-authorized upgrade through Utils.

Attacker-controlled inputs: In a legitimate bundle, none; implementation, initializer data, slot, and offset are fixed by OPCMv2. A direct caller can choose them but lacks ProxyAdmin ownership.

Required state: ProxyAdmin owns the proxy; target uses OZ-v4 one-byte Initializable state. Messenger uses slot 0 offset 20; all other U21 targets use slot 0 offset 0.

State mutation: `StorageSetter -> real+initializer -> StorageSetter -> real`. First pass clears exactly the initializer byte. Second pass checks the OZ-v5 namespaced slot and writes no application field. Initializer state is restored to 2/3/1 as appropriate.

External calls: ProxyAdmin upgrades, StorageSetter reads/writes, and the target initializer.

Cross-contract dependency: Correct slot/offset selection and atomic ProxyAdmin execution. The second pass detects an implementation that wrote OZ-v5 Initializable state.

Broken or weakened assumption: While StorageSetter is installed, the proxy exposes permissionless arbitrary slot setters; safety depends on there being no inter-transaction window or reentrant route during that interval.

Candidate compositions: Reentrancy from an initializer while the setter is installed; wrong initializer byte offset; a batcher that commits between transitions.

Evidence: 132 ERC1967 `Upgraded` logs are exactly 33 four-event sequences in `decoded-logs.json`; resolved/chugsplash proxies follow their legacy routes. `proxy-implementation-map.json` shows unchanged initializer bytes and locked implementations. `test_directStorageSetterCallWritesOnlySingletonStorage` proves a direct singleton call cannot write a proxy.

Confidence: High.

Reason it may be benign: All transitions occur in one EVM transaction, and no external untrusted call occurs while a target is executing StorageSetter code.
