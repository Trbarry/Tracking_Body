PRIM-ID: PRIM-0405 - the real U21 transaction can be re-executed in-process on the pre-upgrade fork

Source contracts: Safe `0x5a0Aae59…`, Multicall3 delegatecall, OPContractsManagerV2 (whole U21 call tree)
Exact functions: `Safe.execTransaction` with the original calldata (evidence/u21-upgrade-tx.json `input`)
Trigger: `vm.createSelectFork("l1pre"); vm.prank(0xE10A25d4…, 0xE10A25d4…); SAFE.call(input)` succeeds: the
  signatures/approved hashes are valid at block 26430858 and nothing in the upgrade depends on block.timestamp,
  so it also succeeds after `vm.warp(+8 days)`.
Attacker-controlled inputs: none (tooling primitive).
Required state: fork at 26430858.
State mutation: the complete U21 state transition (portal 5.8.0 -> 6.1.0 etc.) applied on top of arbitrary
  pre-upgrade state prepared in the test.
Broken or weakened assumption: none. This is the standard-of-proof tool for cross-version claims: prepare an
  object under v8 rules, run the real upgrade, consume it under v9 rules.
Candidate compositions: any lane asking "what if X was in flight when U21 executed" (games in progress, bonds in
  DelayedWETH, a paused identifier, an unresolved ZK/permissioned game, deposits mid-resource-metering).
Evidence: `CrossVersion.t.sol::test_provenV8_upgrade_finalizeV9` (2000 ETH withdrawal proven at 26429408, upgrade,
  finalized under v9: lockbox -2000, message successful) and `::test_failedV8_upgrade_replayV9` (119.59 ETH
  message failed under v8 with recipient code SUBSTITUTED by vm.etch, upgrade, replayed under v9 exactly once;
  `failedMessages`, `finalizedWithdrawals` and the L1CDM balance survive the StorageSetter round-trip).
Confidence: high.
Reason it may be benign: it is a method, not a weakness.
