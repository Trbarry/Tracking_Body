PRIM-2305: Shared-lockbox migration aggregates custody atomically but leaves old authorization monotonic

Source contracts: OPContractsManagerMigrator, OptimismPortal2, ETHLockbox

Exact functions: `migrate`, `_migratePortal`, `migrateLiquidity`, `receiveLiquidity`, `migrateToSharedDisputeGame`

Trigger: Planned owner-controlled interop migration.

Attacker-controlled inputs: None in the production owner path; a withdrawal can later choose an old lockbox as target.

Required state: Same owner and SuperchainConfig, unpaused non-CGT chains, INTEROP initially false, distinct ordered L2 chain IDs.

State mutation: New lockbox authorizes portal; feature flags/pointers change; portal balance and then entire old lockbox balance move to the new pool; old authorization entries are not revoked.

External calls: OPCM upgrades several proxies and calls both old and new lockboxes and portals in one transaction.

Cross-contract dependency: Correctness relies on owner-delegatecall execution and all steps reverting together.

Broken or weakened assumption: `authorizedPortals` and `authorizedLockboxes` are append-only; the current portal bad-target check names only the current lockbox.

Candidate compositions: Old-lockbox target after planned migration; migration interrupted by a newly reachable external callback; shared proof-domain error.

Evidence: v9 `src/L1/opcm/OPContractsManagerMigrator.sol:129-328,475-555`; `src/L1/OptimismPortal2.sol:515-571`; `src/L1/ETHLockbox.sol:180-235`.

Confidence: High for code structure; future migration not active at the observed blocks.

Reason it may be benign: Production migration is privileged and atomic. During a withdrawal callback, old-lockbox `unlockETH` rejects non-default `l2Sender`; `lockETH` only strands the caller's own withdrawn value.
