PRIM-ID: PRIM-1102 — Forced `failedMessages` for ANY finalizable messenger withdrawal, at any gas, by finalizing it from inside an L1CDM replay (portal guard not engaged); value parked in L1CDM

Source contracts:
- OptimismPortal2 v6.1.0 (`0xbEb5…06Ed`), L1CrossDomainMessenger v2.13.0 (`0x25ac…5fA1`), ETHLockbox v2.0.0
- identical behaviour on v8 (portal 5.8.0 / L1CDM 2.11.1) — NOT introduced by U21

Exact functions:
- `CrossDomainMessenger.relayMessage` — replay branch (src/universal/CrossDomainMessenger.sol:244-248),
  re-entrancy branch `xDomainMsgSender != DEFAULT_L2_SENDER` → `failedMessages[hash] = true; return`
  (:265-281), `xDomainMsgSender = _sender` before the target call (:284-285)
- `OptimismPortal2.finalizeWithdrawalTransactionExternalProof` (src/L1/OptimismPortal2.sol:577-666):
  its only re-entrancy guard is `l2Sender != DEFAULT_L2_SENDER` (:594), which is NOT set while a
  message is being REPLAYED directly on the messenger.

Trigger (permissionless):
1. Attacker owns one failed message `Ma` on L1CDM (send any L2→L1 message to a contract of his that
   reverts on first delivery; cost: one withdrawal).
2. Attacker calls `L1CDM.relayMessage(Ma…)` (replay). Messenger sets `xDomainMsgSender` and calls the
   attacker's contract.
3. Inside, the attacker calls `PORTAL.finalizeWithdrawalTransactionExternalProof(victimTx, victimSubmitter)`
   for any mature, valid victim messenger withdrawal. Portal checks pass, lockbox unlocks the value,
   portal calls `L1CDM.relayMessage(Mv)` with `msg.sender == portal && l2Sender == L2CDM`.
4. Messenger sees `xDomainMsgSender != DEFAULT_L2_SENDER` → records `failedMessages[Mv] = true`,
   keeps `msg.value`, returns normally → portal emits `WithdrawalFinalized(success=true)`.

Attacker-controlled inputs: which victim withdrawal, when, and the surrounding call context. Gas is
irrelevant (the failure is not an out-of-gas failure, so v9's `OptimismPortal_L1CDMCallFailed`
revert does not apply — the messenger call SUCCEEDS).

Required state: victim withdrawal proven by anyone, mature, game claim-valid, not paused.

State mutation:
`finalizedWithdrawals[Wv] = true`; `failedMessages[Mv] = true`; `successfulMessages[Mv] = false`;
lockbox −value; **L1CDM +value** (parked outside the lockbox); portal 0.

External calls: attacker → L1CDM → attacker → portal → lockbox.unlockETH → portal.donateETH → L1CDM.

Cross-contract dependency: two independent re-entrancy guards (portal `l2Sender`, messenger
`xDomainMsgSender`) that are not engaged by the same entry points.

Broken or weakened assumption:
"A messenger withdrawal finalized with enough gas is delivered" — it can be forced into the
failed/replayable state by a third party regardless of gas. U21's stated goal for the messenger
path ("revert so the withdrawal stays unfinalized … instead of being finalized with no way to
replay it") is NOT violated: the message IS replayable and the value is held for it.

Candidate compositions:
- any consumer that treats `WithdrawalFinalized(success=true)` or `finalizedWithdrawals` as
  "delivered" (bridges/relayers/accounting off-chain);
- ETH parked in L1CDM is outside the ETHLockbox: check lockbox-level accounting assumptions in
  interop migration (`ETHLockbox.migrateLiquidity`, `OptimismPortal.migrateLiquidity`) — parked
  value does not migrate with the lockbox;
- targets whose handler is NOT replay-safe (reverts permanently after some deadline) → value stuck
  in L1CDM forever; with a time-sensitive L1 handler the attacker picks the ordering.

Evidence:
- `test/poc/NestedReplay.t.sol::test_nested_finalize_inside_replay_forces_failed_state` — PASS on
  `l1` (v9) and `l1pre` (v8). Victim = real fixture f1 class `pre_mature_valid` (messenger, 0.0005 ETH,
  finalizable at the pin with no setup). Attacker message is harness-injected (`vm.store` of his own
  `provenWithdrawals` entry) — in production he just sends it from L2.
  Asserts: nested finalize ok; victim `finalizedWithdrawals` true, `successfulMessages` false,
  `failedMessages` true; lockbox −value, L1CDM +value; later replay by an unrelated EOA delivers
  exactly once and drains L1CDM back; second replay / second finalize revert.
- Invariant campaign (`PortalInvariants.t.sol`): `L1CDM.balance == Σ value of failed-not-yet-relayed
  messages` held on every call.

Confidence: high (executed against real bytecode on both forks).

Reason it may be benign:
Griefing only: the victim (or anyone) replays with one extra L1 transaction; value is conserved
and committed to the message hash; LANE_CONTEXT §6 lists specific-gas message griefing as
not-a-finding and this is the gas-independent sibling. Pre-existing in v8.
