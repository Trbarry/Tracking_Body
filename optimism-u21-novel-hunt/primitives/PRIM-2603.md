PRIM-ID: PRIM-2603 — expired pauses retain a nonzero timestamp and can be reactivated by extend
Source contracts: SuperchainConfig v2.5.0
Exact functions: pause, unpause, extend, pausable, paused, expiration
Trigger: Let 7,884,000 seconds elapse after pause; Guardian then calls extend or unpause.
Attacker-controlled inputs: None; only Guardian can write.
Required state: `pauseTimestamps[id] != 0` and pause expired.
State mutation: Expiry changes only the view result. `extend` resets timestamp and reactivates; `unpause` clears it. A fresh `pause` reverts while timestamp remains nonzero.
External calls: None.
Cross-contract dependency: All U21 pause consumers rely on the boolean view, not raw timestamp.
Broken or weakened assumption: “Not currently paused” does not imply `pausable(id)==true` or that a new pause call will succeed.
Candidate compositions: Guardian tooling races at expiry; monitoring that equates a nonzero timestamp with active pause.
Evidence: `src/L1/SuperchainConfig.sol:31-40,79-127,139-163`; fork test `PauseMatrixTest.test_pauseExpiryRequiresExtendOrUnpauseBeforeRepause`.
Confidence: High.
Reason it may be benign: Explicit Guardian-only lifecycle; no unprivileged way to force expiry handling.
