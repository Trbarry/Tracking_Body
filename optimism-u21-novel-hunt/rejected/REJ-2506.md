# REJ-2506 — stored non-game/no-code address enables deletion or reentrancy

## Idea

Because deletion calls `status()` on the stored address, a fake/reentrant/no-code game might return challenger-wins or manipulate portal state.

## Killing fact

All v7/v8/v9 proof paths fetch a factory index and require ASR properness/registration before storing the address (v8 `OptimismPortal2.sol:396-412`; v9 `:411-427`; ASR `:286-300`). Factory creation deploys and initializes a clone before recording it (`DisputeGameFactory.sol:142-225`). Existing game clones have fixed implementations; relevant sources expose no selfdestruct or upgrade hook. A view-interface `status()` compiles to a static call, preventing state-changing reentrancy. Older pre-fault-proof data is isolated in legacy slot 52, now a spacer (`OptimismPortal2.sol:64-67`); deletion reads the newer nested mapping at slot 57, so legacy raw values cannot become stored game addresses here.

If storage is synthetically pointed at no code, ABI decoding reverts before blacklist is checked, so deletion cannot occur even if blacklisted (`test_noCodeStoredGameRevertsEvenIfBlacklisted`). This is cleanup denial in an unreachable/corrupt state, not deletion of a valid proof.

Disposition: Rejected; only privileged malicious implementation registration or storage corruption could create it.
