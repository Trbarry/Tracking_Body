REJ-0111: Validator validates address X while the upgrade mutated address Y

Idea: `OPContractsManagerStandardValidator` might derive the contracts it checks differently from how `OPContractsManagerV2` derives the contracts it upgrades.

Killing facts:
- Both start from the same SystemConfig and walk the same getters (`systemConfig.optimismPortal()`, `portal.ethLockbox()`, `portal.anchorStateRegistry()`, `systemConfig.disputeGameFactory()` = `portal.disputeGameFactory()`, `systemConfig.delayedWETH()`); `StandardValidatorUtils.sol:132, 365, 403` compare the WETH's and ASR's `ethLockbox()` with the portal's.
- Expected implementation addresses stored in the validator equal the container's (`validate` returns no `*-20` implementation error on any chain).
- Result on chain: `""` for OP, Ink, Unichain with `cannonKonaPrestate = 0x03e5a548...` and the current proposer; `SYSCON-140` when a wrong chain id is supplied (control). The only caller-supplied expectations are prestate, chain id and proposer.
- Residual, not a vulnerability: the 4-field `validate` overload passes `cannonKonaPrestate = 0` and therefore always reports `SCKDG-40` on a healthy super-root chain; Soneium fails `SCKDG-SHAPE,SCKDG-10` because it is permissioned-only. Both are tooling/standardness signals.
