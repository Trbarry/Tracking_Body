# REJ-2902 — Steal funds or protocol authority through a sibling portal's L2 deposit alias

**Idea.** A chain-A withdrawal targets portal B and calls `depositTransaction` with zero mint but
attacker-selected L2 value/data. The derived chain-B transaction executes as the alias of portal A,
potentially spending that alias's balance or bypassing an alias-based authorization check.

**Status:** Rejected as a candidate; retained as PRIM-2902.

**Exact killing facts:**

- The primitive is real. `_isUnsafeTarget` is instance-local (`OptimismPortal2.sol:845-849`),
  deposit mint (`msg.value`) and L2 call value (`_value`) are independent
  (`OptimismPortal2.sol:741-794`), and the fork test emits a zero-mint/nonzero-value sibling deposit.
- Passive reads on all four L2s found every one of the 16 portal-alias/target-chain combinations at
  zero balance, zero nonce, and no code (`mirror/lane-29/LIVE_STATE.md`). There is no deployed asset
  to drain.
- No v9 core L2 contract authorizes an L1 portal alias. `L2CrossDomainMessenger` instead checks the
  alias of its paired L1 messenger (`L2/L2CrossDomainMessenger.sol:101`); generic
  `CrossDomainOwnable` only matters if an application deliberately configures such an owner.
- A target portal cannot create its *own* alias context because self-targeting is rejected. The L1
  messenger likewise blocks its own portal as a relay target
  (`L1/L1CrossDomainMessenger.sol:141-143`). Cross-chain messenger aliases were also empty.

The remaining scenario requires a victim to strand funds at a contract alias or an application to
configure that cross-portal alias as privileged. The former is explicitly suppressed and the
latter was not found in protocol code.
