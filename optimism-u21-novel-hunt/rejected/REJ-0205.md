REJ-0205 — Re-running `SystemConfig.initialize` silently changes L2-derived parameters or ownership

Idea: `initialize` recomputes `scalar` from `basefeeScalar/blobbasefeeScalar` (src/L1/SystemConfig.sol:386-396), zeroes
`overhead`, decodes `batcherHash` as an address (OPContractsManagerV2.sol:600-608, 841), re-emits BATCHER / FEE_SCALARS /
GAS_LIMIT `ConfigUpdate` events and resets the owner. A chain whose stored `scalar` was inconsistent with the two uint32
fields (legacy `setGasConfig`, removed in v8) or whose batcher hash had high bits would get different L2 fee parameters
or a different batcher after the upgrade.

Killing facts:
- Net delta of the tx on the four SystemConfig proxies = implementation slot + `OPCM_SLOT` only
  (evidence/lane02/u21-tx-prestate-diff.json). Slots 51 (owner), 101-108 and all hashed address slots are unchanged.
- At N-1 `scalar == (1 << 248) | (blobbasefeeScalar << 32) | basefeeScalar` on all four (e.g. OP
  `0x01..0f79c50000146b`, slot 104 = `..000f79c5 0000146b 0000000002625a00`), `overhead == 0`, batcher hashes are plain
  addresses, `LEGACY_BATCH_INBOX_SLOT == 0`.
- Fields not handled by `initialize` (EIP-1559 params, operator fee, DA footprint, `minBaseFee`) were not touched and no
  event was emitted for them.
- `startBlock` unchanged (`_setStartBlock` only writes when 0).
