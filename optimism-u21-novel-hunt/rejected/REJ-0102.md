REJ-0102: Calling the OPCM family directly (CALL) or from an attacker contract (DELEGATECALL)

Idea: the OPCM is meant to be DELEGATECALLed by the ProxyAdmin owner; a direct call, or an attacker delegatecall, or the unguarded external `OPContractsManagerUtils.upgrade` / `loadOrDeployProxy`, might mutate a live chain.

Killing facts:
- `upgrade`, `upgradeSuperchain`, `migrate` start with `_onlyDelegateCall()` (`OPContractsManagerV2.sol:198, 245, 294, 1074-1078`): direct CALL with the real U21 calldata reverts `OPContractsManagerV2_OnlyDelegateCall()` (test `test_directCall_upgrade_reverts`).
- An attacker contract delegatecalling the OPCM with the real OP Mainnet input reaches `ProxyAdmin.upgrade` as itself and reverts `Ownable: caller is not the owner` (test `test_attackerDelegatecall_upgrade_reverts`, revert data logged).
- `OPContractsManagerUtils.upgrade` called directly makes the Utils contract the caller of `ProxyAdmin.upgrade`: revert, portal implementation unchanged (test `test_directCall_utilsUpgrade_reverts`).
- OPCM v9, Utils, Container, Migrator, Validator and StorageSetter hold no ETH and own nothing: the OPCM/Utils/Migrator/StorageSetter have no storage variables (`snapshots/storageLayout/*.json` are empty), the Container only stores blueprint/implementation addresses, the StandardValidator stores constructor-set expectations and exposes no setter, and no live contract has any of them as owner, admin, guardian or authorised portal/lockbox (wiring table in `lanes/LANE-01-report.md`). `SystemConfig.lastUsedOPCM` is metadata only (read by `isPermittedUpgradeSequence`), it grants nothing.
