REJ-0601 — "U21 changed the pause identifier, so a pre-existing pause was lost / an old one resurrected"

Idea: v8 SystemConfig.paused() used the portal address when ETH_LOCKBOX was off and the lockbox when on; v9 always uses the lockbox. A chain paused (or holding an expired, never-reset timestamp) under the old identifier could become unpaused, or a stale timestamp on the new identifier could re-activate.

Killing facts:
- All four upgraded chains ALREADY had ETH_LOCKBOX = true and the SAME lockbox address in portal.ethLockbox() at block 26430858 (one block before U21): OP 0x322b47Ff…, Ink 0xbd4AbB32…, Soneium 0x67B4de6F…, Unichain 0x08bA0023… (evidence/lane06/state-pre-26430858.txt vs state-post-26433900.txt). The identifier did not change for them.
- SuperchainConfig.pauseTimestamps is 0 for address(0), all four lockboxes and all four portals, pre and post. No Paused/Unpaused/FeatureSet log in the U21 receipt (307 logs scanned).
- For a chain that DOES switch (ETH_LOCKBOX off -> on): setFeature reverts while `superchainConfig.paused(optimismPortal())` (SystemConfig.sol:552) so the v9 upgrade cannot unpause it; the global pause keeps applying through ETHLockbox.paused() -> isLocalOrGlobalPaused. A v8 chain with the flag on but portal.ethLockbox()==0 had identifier address(0) (global only), so nothing chain-specific can be lost there either.
