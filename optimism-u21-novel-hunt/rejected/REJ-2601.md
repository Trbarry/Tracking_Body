# REJ-2601 — stale Portal pause identifier leaves a value path live

**Hypothesis.** A U21 consumer still keys its pause to the old Portal identifier, so a Guardian lockbox pause would not stop it.

**Killed by.** Every deployed resolver on OP, Ink, Soneium, and Unichain returned true after pausing that chain's lockbox in a fork. Portal/SystemConfig follow the Portal's current lockbox; ASR and DelayedWETH store the same lockbox; messenger and both bridges follow SystemConfig. Prove, finalize, relay, bridge finalization, lockbox unlock, and DelayedWETH withdrawal all reverted before value release.

**Exact evidence.** `src/L1/ETHLockbox.sol:111-114`; `src/L1/OptimismPortal2.sol:305-307`; `src/L1/SystemConfig.sol:570-576`; `src/dispute/AnchorStateRegistry.sol:135-143`; `src/dispute/DelayedWETH.sol:98-108`; `PauseMatrixTest.test_lockboxIdentifierPausesAllDependantsOnAllFourChains` and `.test_valueMovingAndStatePathsUnderLockboxPause` pass against block 26,430,859.

Pausing the old Portal identifier is indeed ineffective post-U21, but all pre/N/later timestamps for global, four Portals, and four lockboxes were zero, and all four chains already used lockbox identifiers at N-1. This is stale-tooling risk, not a contract bypass.
