# REJ-2301 — Reentrant or repeated finalization double-unlocks ETH

## Hypothesis

Because v9 sets `finalizedWithdrawals` before unlocking and calls an arbitrary target
after unlocking, the target might reenter finalization and obtain a second unlock.

## Killing fact

The target callback begins only after `l2Sender` is set. Every nested finalization
fails at `OptimismPortal_NoReentrancy` before proof checking or unlock
(`OptimismPortal2.sol:591-615`). After the callback, the already-set finalized bit
blocks an ordinary second attempt (`OptimismPortal2.sol:676-685`). Any later revert
rolls both state changes and the unlock back atomically.

## Evidence

`test_realProofEtchedReentrantFinalizeCannotDoubleUnlock` uses a real mature proof
and deployed portal/lockbox code, with only the fixed historical target code etched
locally. It observes one exact unlock and the expected nested revert. The unmodified
real finalization then rejects a second call with `OptimismPortal_AlreadyFinalized`.

## Conclusion

Killed. The target substitution is modeled-only, but it exercises the deployed
guard at the strongest possible callback point and finds no double unlock.
