REJ-0207 — The pause-identifier change (portal -> lockbox) leaves a stale pause, silently unpauses a chain, or strands the Guardian's ability to re-pause

Idea: v9 resolves every chain pause through the lockbox identifier. A chain that used the portal identifier before U21
with a non-zero `pauseTimestamps[portal]` would become unpaused; an expired-but-non-zero `pauseTimestamps[lockbox]` would
make `SuperchainConfig.pause(lockbox)` revert `AlreadyPaused` (src/L1/SuperchainConfig.sol:82-94).

Killing facts (SuperchainConfig `0x95703e09..`, blocks 26430858 / 26430859 / 26433900):
- `pauseTimestamps` = 0 for `address(0)`, the four portals and the four lockboxes; `paused(x)` false for all nine.
- `isFeatureEnabled(ETH_LOCKBOX)` was already true and `portal.ethLockbox()` already non-zero on all four chains at N-1,
  so v8 `SystemConfig.paused()` already used the lockbox identifier: no identifier switch happened.
- `portal.paused() == systemConfig.paused() == asr.paused() == lockbox.paused() == l1cdm.paused() == false` before and
  after; guardian `0x09f7150D..` unchanged; `pauseExpiry` 7,884,000 s unchanged.
- `SuperchainConfig.paused(address)` kept its v8 semantics (identifier-only); other chains sharing this SuperchainConfig
  and still on v8 are unaffected.
