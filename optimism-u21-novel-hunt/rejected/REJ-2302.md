# REJ-2302 — Failed target strands withdrawable ETH in portal or relocks surplus

## Hypothesis

A failed target CALL might leave unlocked ETH in the portal for a later attacker, or
the failure branch might sweep unrelated donated/forced ETH into the lockbox and
misaccount it as the withdrawal.

## Killing fact

For a non-messenger withdrawal, v9 re-locks exactly `_tx.value`, not
`address(this).balance` (`OptimismPortal2.sol:655-665`). A reverting CALL transfers
no value, so exactly the transient unlock remains available for relock. Pre-existing
portal surplus is unchanged. For an L2-messenger withdrawal whose outer call fails,
`OptimismPortal_L1CDMCallFailed` reverts the entire transaction
(`OptimismPortal2.sol:639-653`). If only the messenger's inner target fails, the
messenger itself returns normally, retains the value, records `failedMessages`, and
backs replay (`CrossDomainMessenger.sol:239-306`).

## Evidence

The modeled direct-withdrawal failure test leaves a 2 ETH portal surplus unchanged
and lockbox balance net unchanged. The real-proof/etched-messenger failure test
restores finalized=false and both balances. Both substitutions are explicitly
modeled-only; the real successful fixture confirms the live path.

## Conclusion

Killed. Each failure class has exactly one backing location; no public full-balance
sweep or orphaned transient unlock was found.
