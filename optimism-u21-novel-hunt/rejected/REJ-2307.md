# REJ-2307 — No per-portal ledger alone permits shared-pool insolvency

## Hypothesis

Because `unlockETH` checks only the aggregate lockbox balance and has no per-portal
quota, any caller might assign itself another chain's backing.

## Killing fact

Only an authorized portal can call `unlockETH`, and the portal reaches it only after
a mature proof passes and the withdrawal hash is unfinalized
(`ETHLockbox.sol:157-174`; `OptimismPortal2.sol:603-615,671-705`). Portal
authorization requires shared ProxyAdmin owner and SuperchainConfig
(`ETHLockbox.sol:218-235`). The planned migrator rejects zero, duplicate, and
unordered L2 chain IDs, explicitly addressing proof-domain aliasing
(`OPContractsManagerMigrator.sol:291-328`). Current OP INTEROP=false and its pool is
not shared with the sibling portals.

## Evidence

Unauthorized `lockETH`, `unlockETH`, and `receiveLiquidity` calls revert in fork
tests. State reads show only the OP portal authorized on its current per-chain
lockbox for the reviewed flow.

## Conclusion

Killed as a standalone attack. Pooling does enlarge the blast radius of any separate
proof-domain or authorized-portal bug, so that composition remains high value.
