REJ-0405 - "sender == L2CrossDomainMessenger but target != L1CrossDomainMessenger" (bypass or abuse of the sender-only check)

Idea: make the L2 messenger the `msg.sender` of `L2ToL1MessagePasser.initiateWithdrawal` with an arbitrary L1
target (e.g. via an L1->L2 message relayed to the passer). Such a withdrawal would be un-finalizable when it
fails (attacker does not care) - or, reversed, look for a messenger message that travels with a non-messenger
sender and therefore loses the new protection.

Killing facts:
- deployed L2CDM (OP Mainnet, v2.2.1, block 159654093) rejects relay targets `address(this)` and
  `0x4200…0016` with "cannot send message to blocked system address"; `sendMessage` hard-wires the withdrawal
  target to `otherMessenger = 0x25ace71c…` (L2Side.t.sol, both tests pass on the `l2` fork).
- no L1 address aliases to 0x4200…0007 without a preimage/private key.
- so on the live L2 code: sender == L2CDM  <=>  canonical messenger message to the L1CDM. The portal's branch
  itself is target-independent (Fab.t.sol::test_cond_senderL2CDM_targetNotL1CDM_reverting, fabricated proof).
Not checked: Ink / Soneium / Unichain L2 predeploy versions (no local L2 fork for them).
