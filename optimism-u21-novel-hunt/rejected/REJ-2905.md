# REJ-2905 — Retired per-chain lockbox becomes a permissionless value sink or drain

**Idea.** Migration leaves the source portal authorized on its emptied old lockbox. A withdrawal
targets that old box to move shared funds out, or uses its sticky authorization to drain it/shared
liquidity.

**Status:** Rejected for eligible impact.

**Exact killing facts:**

- `lockETH` on the source chain's retired box can succeed because authorization is sticky. But the
  only ETH it can receive through the withdrawal target call is that same withdrawal's `_tx.value`,
  already burned on L2. Shared liquid assets and aggregate circulating liabilities both fall by
  the same amount. The actor strands its own withdrawal.
- `unlockETH` is killed by the non-default `l2Sender` check; `receiveLiquidity` is killed because a
  portal is not an authorized lockbox; `migrateLiquidity` is ProxyAdmin-owner-only
  (`ETHLockbox.sol:132-216`).
- Target failure for a non-messenger withdrawal causes the portal to relock the unlocked value in
  its current lockbox (`OptimismPortal2.sol:659-665`). Thus targeting a sibling old lockbox, whose
  authorization mapping is false, does not leak value to it.
- The migration empties each old box before repointing completes and the validator checks it is
  zero (`OPContractsManagerMigrator.sol:526-543`;
  `OPContractsManagerMigrationValidator.sol:559-567`).

This is a user-controlled self-burn/stranding shape, not theft or insolvency. Sticky authorization
is recorded separately as PRIM-2903 because future governance-domain separation would matter.
