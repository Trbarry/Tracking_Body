# REJ-2901 — Withdrawal target calls shared lockbox `unlockETH` for an arbitrary amount

**Idea.** After migration every portal is authorized on one shared lockbox. A user chooses the
shared lockbox as a withdrawal target and supplies `unlockETH(largeAmount)` calldata, so the portal
appears as the authorized caller.

**Status:** Rejected.

**Exact killing facts:**

1. Both proving and finalization apply `_isUnsafeTarget`; the deployed v9 list rejects the portal
   itself and its *current* `ethLockbox` (`OptimismPortal2.sol:401-404,598-601,845-849`). The
   current lockbox after migration is the shared lockbox.
2. The real block-N portal returns `OptimismPortal_BadTarget` for itself/current lockbox. The same
   transaction shape reaches `OptimismPortal_Unproven` for a sibling portal/lockbox, proving this
   is the actual deployed filter rather than only a source claim
   (`test_realPortalBlocksOnlyItselfAndItsCurrentLockbox`).
3. A retired old lockbox is no longer the current bad target, but `unlockETH` calls the authorized
   caller portal's `l2Sender()` and requires the default value (`ETHLockbox.sol:157-174`). During
   withdrawal target execution the source portal has already set `l2Sender = _tx.sender`
   (`OptimismPortal2.sol:617-630`), so the old lockbox reverts
   `ETHLockbox_NoWithdrawalTransactions`. The real implementation does so in
   `test_realLockboxRejectsAuthorizedPortalDuringWithdrawalContext`.
4. A sibling retired lockbox does not authorize the source portal; the live cross-product is
   diagonal. `receiveLiquidity` needs lockbox authorization and `migrateLiquidity` needs the
   ProxyAdmin owner.

No route was found that makes an idle authorized portal call amount-arbitrary `unlockETH`.
