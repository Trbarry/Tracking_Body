# REJ-2404 — Messenger returns success to Portal without delivery or replay record

## Idea

Find a messenger path where the low-level Portal→messenger call returns true, yet the application was not called and neither `failedMessages` nor `successfulMessages` is set.

## Killing fact

Every normal messenger non-delivery path after message hashing either records `failedMessages` and returns (`CrossDomainMessenger.sol:256-281`) or records failure after the target returns false (`:284-306`). Preconditions that revert before recording—pause, bad version, legacy already-successful, caller/value mismatch, unsafe target, or already successful—cause Portal `SafeCall` to return false. For a genuine L2 messenger withdrawal, v9 then reverts the entire Portal finalization (`OptimismPortal2.sol:639-653`).

Fork tests cover both sides: recorded failure leaves messenger replay (`WithdrawalFinalization24.t.sol:359-399`); pre-record revert leaves the Portal unfinalized (`:401-428`). No unrepresented terminal state survived.
